
Agent Platform:

========================================
1. AGENT RUNTIME
========================================

This runtime executes the agents. This acts as runtime for agents. 
The agents are run through a standard interface.

The runtime supports a loop where agents, humans interact. 

Enhanced Agent Class/Entity:

   # Identity & Configuration
   agent_id: Unique identifier (UUID)
   agent_type: MASTER | SUB_AGENT
   parent_agent_id: Reference to master (null if master)
   user_id: Owner of this agent
   
   # Core Components
   user_profile: User behavior, preferences, learned interests
   agent_config: Model settings (LLM provider, temperature, max_tokens)
   agent_context: Current conversation/session state
   memory_module: 
      - short_term_memory: Recent interactions (last N messages)
      - long_term_memory: Vector DB handle for semantic retrieval
      - episodic_memory: Task execution history
   tools_available: Map<tool_name, tool_handler>
   task_queue: Priority queue of pending tasks
   
   # State Management
   status: IDLE | RUNNING | WAITING_APPROVAL | ERROR | TERMINATED
   last_checkpoint: Timestamp of last state save
   
Main Methods:
   Run():
      - Main event loop (listens to message queue, executes tasks)
      - Should be async/non-blocking
      
   execute_tool_call(tool_name, params) -> ToolResult:
      - Validates tool exists
      - Executes with timeout
      - Returns result or error
      
   create_task(task_spec) -> task_id:
      - Creates task in Task Executor
      - Adds to task_queue for tracking
      
   spawn_sub_agent(specialization) -> Agent:
      - Creates child agent with specific role
      - Returns sub-agent reference
      
   send_message(to_agent_id, message):
      - Publishes to Agent Message Channel
      
   receive_message(from_agent_id, message):
      - Callback when message arrives
      - Updates context and triggers response
      
   checkpoint():
      - Saves current state to persistent storage
      - Called periodically or before long operations
      
   terminate():
      - Graceful shutdown (save state, close connections)

OPEN QUESTIONS - Agent Runtime:
Q1. How is an Agent instantiated? Who calls Run()? Does it run in a 
    loop until terminated, or per-request?
    It should be started by the platform. It should run in a loop unless
    terminated explicitly. 
Q2. Can one Agent handle multiple conversations/tasks simultaneously, 
    or is it single-threaded?
    Each agent can create an execution graph/path based on DAG (Directed
    Acyclic Graph), Based on this the execution can be done parallel / sync 
    based on the dependencies. 
Q3. When/how are user_profile, Agent_context, and memory_module saved 
    to DB? After each interaction? Periodic snapshots?
    Whatever happens in the agent, either action, memory update, 
    task update should be written to DB (persisted even if VM or execution
    crashes . )
Q4. Does execute_tool_call() run synchronously or async? What if a tool 
    takes minutes/hours (e.g., web scraping)?
    Execute tool call should not block the execution of the agent. 
    This should be again based on the DAG Graph.
Q5. Is receive_message() polled or event-driven (callback)? How does the 
    agent know when messages arrive?
    The receive message should be based on event-driven. The platform 
    will notify the agent on receiving a message. 
Q6. What happens if Run() crashes? Auto-restart? Error logged and agent 
    marked failed?
    Auto restart should happen from the last working point in the loop.

2. TASK EXECUTOR
========================================

The task execution environment / service runs the tasks 
that are created by the agents and designated to run 
in isolation / background. It should follow the pre-defined task 
schema. 

Enhanced Task Schema:
   # Identity
   task_id: Unique identifier
   agent_id: Creator agent
   parent_task_id: For sub-tasks (null if root)
   
   # Definition
   task_type: RESEARCH | EXPLORATION | PURCHASE | BOOKING | CUSTOM
   task_description: Natural language description
   task_params: Structured parameters (JSON)
   priority: 1-10 (10 = highest)
   
   # Execution
   execute() -> TaskResult:
      - Main execution logic
      - Should be idempotent (can retry safely)
      - Returns structured result
   
   # Resources
   llm_config: LLM settings if needed
   tools: List of tool names this task uses
   max_duration: Timeout in seconds (default: 300)
   max_retries: Retry attempts on failure (default: 3)
   
   # State
   status: PENDING | RUNNING | COMPLETED | FAILED | CANCELLED
   created_at: Timestamp
   started_at: Timestamp
   completed_at: Timestamp
   result: Output data (populated on completion)
   error: Error message if failed
   
   # Callbacks
   on_complete(result): Notify agent of completion
   on_failure(error): Notify agent of failure
   on_progress(percent): Progress updates (optional)

Task Executor Service:
   task_queue: Priority queue (ordered by priority, then FIFO)
   active_tasks: Map<task_id, Task>
   max_concurrent_tasks_per_user: Configurable limit
   
   Methods:
   submit_task(task: Task) -> task_id:
      - Validates task schema
      - Enqueues task
      - Returns task_id for tracking
      
   execute_task(task_id):
      - Spins up isolated runtime (container/process)
      - Injects tools and LLM access
      - Monitors execution with timeout
      - Captures result/error
      - Triggers callback to agent
      
   cancel_task(task_id):
      - Stops running task
      - Marks as CANCELLED
      
   get_task_status(task_id) -> TaskStatus:
      - Returns current state and progress

3. AGENT MESSAGE CHANNEL
========================================

The agent message channel in the platform helps in the communication
between the agents. The communication should follow a standard format.

Enhanced Message Schema:
   # Routing
   message_id: Unique identifier (UUID)
   from_agent_id: Sender agent
   from_user_id: Sender's owner (for cross-user privacy checks)
   to_agent_id: Recipient agent
   to_user_id: Recipient's owner
   
   # Content
   message_type: QUERY | RESPONSE | TASK_REQUEST | TASK_RESULT | 
                 APPROVAL_REQUEST | NOTIFICATION
   message_body: {
      content: Actual message/data
      metadata: {
         thread_id: For conversation threading
         reply_to: For responses (references message_id)
         urgency: LOW | MEDIUM | HIGH
      }
   }
   
   # Lifecycle
   timestamp: Message creation time
   expires_at: TTL for ephemeral messages
   status: PENDING | DELIVERED | READ | FAILED
   
   # Privacy
   requires_approval: Boolean (for cross-user messages)
   approved_by_user: Boolean (recipient user consent)

Agent Message Channel Service:
   message_broker: Underlying transport (Kafka topic, RabbitMQ queue)
   agent_registry: Directory service (agent_id -> connection_info)
   message_store: Persistent storage for message history
   
   Methods:
   send_message(message: Message) -> message_id:
      - Validates sender agent exists
      - Checks privacy rules (cross-user consent)
      - Publishes to message_broker
      - Stores in message_store
      - Returns message_id
      
   route_message(message_id):
      - Looks up recipient agent in registry
      - Delivers message to agent's inbox
      - Updates status to DELIVERED
      
   subscribe_agent(agent_id, callback):
      - Registers agent to receive messages
      - Callback invoked when message arrives
      
   get_message_history(agent_id, thread_id) -> List[Message]:
      - Retrieves conversation history
      - For context reconstruction

8. SYSTEM FLOWS
========================================

--- Agent Lifecycle Flow ---

User Signs Up → Platform Creates Master Agent → Agent.Run() starts
   ↓
Agent enters event loop:
   - Check message queue
   - Check task queue
   - Execute pending actions
   - Checkpoint state
   - Sleep/wait for next event
   ↓
User Sends Message → Agent processes → Calls LLM → Executes tools → Responds
   ↓
Agent creates background task → Task Executor picks up → Executes → Returns result
   ↓
User Deletes Account → Agent.terminate() → Cleanup resources


--- Task Execution Flow ---

Agent creates Task → submit_task(task) → Task Executor
   ↓
Task Executor:
   - Validate task schema
   - Check resource quotas
   - Spin up isolated runtime (container)
   - Inject tools + LLM access
   - Execute task.execute()
   - Monitor with timeout
   ↓
Task completes:
   SUCCESS: Store result → Callback agent → Update task status
   FAILURE: Log error → Retry? → Callback agent with error


--- Cross-User Agent Communication Flow ---

Agent A (User 1) wants to contact Agent B (User 2)
   ↓
Agent A calls send_message(to=Agent_B, message=...)
   ↓
Agent Message Channel:
   - Check if cross-user communication
   - Check User 2's privacy settings
   - IF approval required: Send approval request to User 2
   - ELSE: Route message directly
   ↓
User 2 approves → Message delivered to Agent B
Agent B processes message → Optionally responds

9. CRITICAL DESIGN DECISIONS NEEDED
========================================

DECISION 1: Agent Runtime Environment
   Options: 
      - Containers (Docker/Kubernetes)
      - Serverless functions (AWS Lambda, Cloud Run)
      - Long-running VMs/processes
   Trade-offs: Isolation vs. cold-start latency vs. cost

DECISION 2: Message Broker
   Options:
      - Kafka (high throughput, persistent, complex)
      - RabbitMQ (simpler, flexible routing)
      - Redis Streams (lightweight, limited features)
   Trade-offs: Scalability vs. complexity vs. features

DECISION 3: Agent State Management
   Options:
      - Stateless (reload from DB each request)
      - Stateful (keep in-memory, checkpoint periodically)
      - Hybrid (cache frequently accessed state)
   Trade-offs: Consistency vs. performance vs. complexity

DECISION 4: LLM Strategy
   Options:
      - Always call external APIs (GPT-4, Claude)
      - Self-host smaller models for simple tasks
      - Hybrid (route based on task complexity)
   Trade-offs: Cost vs. latency vs. quality vs. control

DECISION 5: Task Isolation
   Options:
      - Process-level (multiprocessing)
      - Container-level (Docker)
      - VM-level (AWS Fargate)
   Trade-offs: Security vs. overhead vs. complexity

DECISION 6: Approval Mechanism
   Options:
      - Synchronous (block until user approves)
      - Asynchronous (continue other work, apply approval later)
      - Configurable per task type
   Trade-offs: UX responsiveness vs. system complexity

DECISION 7: Technology Stack ✅ DECIDED
   
   CHOSEN STACK:
   
   Core Platform Language: Python 3.11+
      Rationale: Best AI/LLM ecosystem, async-native, sufficient performance
                 for LLM-bound operations, faster development for MVP
   
   Web Framework: FastAPI
      Rationale: Async/await native, auto OpenAPI docs, type safety with 
                 Pydantic, high performance ASGI, excellent for microservices
   
   Agent Runtime: Python (Custom framework with LangChain integration)
      Rationale: Access to full LLM/agent ecosystem, web scraping tools,
                 data processing libraries
   
   Task Executor: Python with Celery + Redis
      Rationale: Mature distributed task queue system, proven at scale
   
   Primary Database: MongoDB Atlas
      Rationale: Flexible schema for evolving agents, change streams for 
                 real-time updates, transactions support, managed cloud option
      Collections:
         - users: User accounts and metadata
         - agents: Agent configurations and state
         - tasks: Task definitions and results
         - messages: Message history
         - events: Audit log
   
   Vector Database: Qdrant (self-hosted) or Pinecone (managed option)
      Rationale: Qdrant for cost-sensitive/control, Pinecone for quick start
      Usage: User profile embeddings, content similarity, memory retrieval
   
   Cache & Message Queue: Redis
      Rationale: Multi-purpose (cache + queue + pub/sub), reduces complexity
      Usage:
         - Agent session state (hot data)
         - Rate limiting counters
         - Task queue backend
         - Pub/Sub for real-time events
   
   Message Broker: Redis Pub/Sub (start) → RabbitMQ (scale)
      Rationale: Redis for simplicity initially, RabbitMQ when routing 
                 complexity increases
   
   Container Orchestration: Docker Compose (MVP) → Kubernetes (production scale)
      Rationale: Docker Compose for single-machine start, K8s for multi-node scale
   
   Web Server: Uvicorn
      Rationale: High-performance ASGI server for FastAPI
   
   Browser Automation: Playwright (Python)
      Rationale: Modern, supports headless, better than Selenium
   
   LLM Integration: Custom abstraction layer + LangChain
      Rationale: Flexibility to swap providers, custom tool calling, MCP support
   
   MINIMAL MVP STACK (Start Here):
      - Language: Python 3.11+
      - Framework: FastAPI
      - Database: MongoDB Atlas (free tier)
      - Vector DB: Qdrant (local Docker)
      - Cache/Queue: Redis (local Docker)
      - Message Broker: Redis Pub/Sub
      - Deployment: Docker Compose (single machine)
   
   MIGRATION PATH:
      - Phase 2: Separate RabbitMQ for complex message routing
      - Phase 3: Kubernetes for multi-node orchestration
      - Phase 4: Managed Qdrant/Pinecone based on scale needs

11. TECHNOLOGY STACK JUSTIFICATION
========================================

WHY PYTHON OVER GO:

1. LLM/Agent Ecosystem Dominance
   - LangChain, LlamaIndex, CrewAI, AutoGPT all Python-native
   - All major LLM providers have best-in-class Python SDKs
   - 10x more agent frameworks and tools available
   
2. AI/ML Libraries
   - Web scraping: BeautifulSoup, Scrapy, Playwright
   - Data processing: Pandas, NumPy
   - Vector DB: Native SDKs for all major providers
   - NLP: HuggingFace Transformers, spaCy
   
3. Development Velocity
   - Faster prototyping for MVP
   - Dynamic typing speeds iteration
   - Rich ecosystem reduces wheel reinvention
   
4. Performance is NOT the Bottleneck
   - LLM API calls take 1-10 seconds
   - Python's async/await handles I/O-bound workloads well
   - Go's speed advantage irrelevant when waiting for external APIs
   
5. Talent Pool
   - Easier to find AI/ML-focused Python developers
   - Larger community for AI-specific problems

Trade-off Accepted: Go is faster, but Python's ecosystem wins for AI-first platform


WHY FASTAPI OVER DJANGO/FLASK:

1. Async-Native
   - Built on Starlette (async framework)
   - Critical for long-running agent operations
   - Non-blocking I/O for LLM calls
   
2. Modern Developer Experience
   - Type hints + Pydantic validation
   - Auto-generated OpenAPI/Swagger docs
   - Dependency injection system
   
3. Performance
   - On par with Node.js/Go for I/O-bound tasks
   - Much faster than Django
   
4. Microservices-Ready
   - Lightweight, composable
   - Easy to split into services later

Django Rejected: Not async-first, heavier weight, overkill for API-first platform
Flask Rejected: No built-in async, less modern, manual setup


WHY MONGODB OVER OTHER NOSQL:

1. Flexibility
   - Schema-less: agents/tasks evolve rapidly
   - Easy to add fields without migrations
   
2. Change Streams
   - Real-time notifications when agent state updates
   - Platform can react to agent events immediately
   
3. Transactions
   - ACID guarantees since v4.0
   - Critical for task state consistency
   
4. Query Capabilities
   - Rich query language (filters, aggregations)
   - Better than DynamoDB's limited queries
   
5. Developer Experience
   - Excellent Python drivers (Motor for async)
   - Atlas managed offering (free tier to start)
   - Familiar document model

DynamoDB Rejected: Complex modeling, no cross-partition queries, AWS lock-in
Firestore Rejected: Limited query capabilities, GCP lock-in


WHY REDIS FOR CACHE & QUEUE:

1. Multi-Purpose
   - Cache (agent session state)
   - Queue (Celery backend)
   - Pub/Sub (message broker start)
   - Rate limiting
   
2. Simplicity
   - Single technology, less operational complexity
   - Reduces infrastructure footprint
   
3. Performance
   - In-memory, microsecond latency
   - Handles high throughput
   
4. Battle-Tested
   - Industry standard
   - Mature Python clients (redis-py, aioredis)


WHY QDRANT OVER PINECONE/WEAVIATE:

1. Cost Control
   - Self-hostable, no per-query charges
   - Pinecone can get expensive at scale
   
2. Performance
   - Written in Rust, very fast
   - Good Python SDK
   
3. Flexibility
   - Advanced filtering with metadata
   - Hybrid search capabilities
   
4. Cloud Option Available
   - Can migrate to managed later if needed

Pinecone Alternative: Use if prefer fully managed, don't want infra management
